Quando escrevo no telemóvel,
para onde vai a mensagem?

Caminho completo de um prompt — da caixa de texto no telemóvel até ao Freebuff a correr no PTY do teu PC, e a resposta a voltar como uma bolha verde. Com a tabela de onde está plaintext e onde está cifrado em cada momento.

ESTADO ACTUAL · Daemon e telemóvel têm E2E_DISABLED = true em daemon/src/index.ts e mobile/app.js. O doc mostra o caminho completo (com a camada AES-GCM nos passos 2 / 6 / 9). Em modo plaintext, a estrutura é a mesma mas não há ciphertext-badge — os envelopes saem como {v:2, type:'plain', …}. Quando o flag volta a false, é o que está descrito aqui.

Conclusão prática: a única "ponte" de plaintext fora do teu controlo é o daemon e o PTY no teu PC. Tudo o que passa pela Cloudflare é opaco — sem chave privada, nunca lê conteúdo. Os tokens de sessão estão em ~/.dispatch/config.json na tua máquina.

Os 10 passos, com código real

Cada passo tem uma localização exata
STEP 01 Escreves na caixa de texto mobile/app.js:388–406

A string entra no DOM do telemóvel e fica numa variável JS. A partir daqui há dois caminhos consoante o flag E2E_DISABLED.

// mobile/app.js
$form.addEventListener('submit', async e => {
  e.preventDefault();
  const text = $input.value.trim();      // "Reply with E2E_WORKS_NOW"
  ...
});
plaintext: SIM local: DOM do PWA
STEP 02 Telemóvel constrói o envelope mobile/app.js:444-460 (encryptEnvelope)

Com E2E ligado: AES-GCM-256 com nonce aleatório de 12 bytes + AAD "v2|client|<seq>". Com E2E desligado: o telemóvel envia directamente um envelope {v:2, type:'plain', ...inner} sem cifrar.

// E2E-on path (encrypt branch)
const nonce = crypto.getRandomValues(new Uint8Array(12));
const plain = new TextEncoder().encode(JSON.stringify(inner));
session.outSeq += 1;
const aad = new TextEncoder().encode('v2|client|' + session.outSeq);
const ct = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv: nonce, additionalData: aad },
  session.sharedKey, plain,
);
return { v: 2, type: 'enc', seq: session.outSeq,
  nonce: btoa(...), ct: btoa(...new Uint8Array(ct)) };
cifrado: AES-GCM AAD: "v2|client|<seq>" nonce: 12B random
STEP 03 Travessia telemóvel → Cloudflare mobile/app.js:65–77 (+ ws URL building)

WebSocket frames UTF-8 JSON, encapsulados em TLS 1.3. O URL traz ?sessionId=X&token=Y&role=client&v=2 — o token é o que pair/redeem te deu, único por role+sessionId.

TLS 1.3 role=client sessionId+token
STEP 04 Cloudflare Worker aceita relay/src/index.ts:55–62 + relay-do.ts:79–112

O router mete a request no Durable Object certo (1 por sessionId). O DO valida o token, valida role+sessionId, e acorda o socket hibernatable.

// relay/src/relay-do.ts
const rec = await this.state.storage.get(`token:${token}`);
if (!rec || rec.expiresAt < Date.now()) return new Response('expired token', { status: 403 });
if (rec.role !== role) return new Response('role mismatch', { status: 403 });
this.state.acceptWebSocket(server, [role, rec.sessionId]);
+ emits {type:'system',event:'ready'} + announces client_connected
STEP 05 Relay forward o envelope (cego) relay/src/relay-do.ts:99–138 (webSocketMessage)

O relay não vê conteúdo, não tem chave. Manda o que recebeu ao daemon. Da mesma forma no sentido inverso, daemon → clients. Nota: o relay também emite 2–3 system events em plaintext (ex: ready, daemon_connected) — esses são só routing/health, nunca conteúdo do utilizador.

// relay/src/relay-do.ts
if (role === 'client') {
  // cliente mandou prompt → reenvia pro daemon (cego)
  for (const peer of this.state.getWebSockets('daemon')) {
    try { peer.send(message); } catch {}
  }
  // também emite system{event:'client_prompt'} para viewers (routing, não conteúdo)
  const sys = JSON.stringify({ type:'system', event:'client_prompt', ... });
  for (const peer of this.state.getWebSockets('viewer')) try { peer.send(sys); } catch {}
}
no decryption here opaque byte-pipe
STEP 06 Daemon decifra (se E2E_on) daemon/src/crypto.ts:119-140 (decryptEnvelope)

Faz AES-GCM decrypt com a sharedKey calculada no handshake. O AAD tem que bater certo ou o auth-tag rejeita e logamos Unsupported state or unable to authenticate data.

// daemon/src/crypto.ts
const decipher = crypto.createDecipheriv('aes-256-gcm', state.sharedKey, nonce);
decipher.setAAD(aadFor('client', env.seq));
decipher.setAuthTag(tag);
const plain = Buffer.concat([decipher.update(data), decipher.final()]);
state.inSeq = env.seq;          // accept ONLY after successful decrypt
return JSON.parse(plain.toString('utf8'));
AES-256-GCM AAD: "v2|client|<seq>" replay window enforced
STEP 07 Daemon escreve no PTY daemon/src/index.ts:244-249 (handleInner → term.write)

O daemon tem um pty.spawn('freebuff'). Escrever no PTY é equivalente a digitar + Enter num terminal humano. O Freebuff recebe como input interactivo.

// daemon/src/index.ts · handleInner()
if (inner.t === 'prompt') {
  log(`prompt received (${inner.text.length} chars)`);
  try {
    term.write(inner.text);
    term.write('\r');                  // carriage return = tecla Enter
  } catch (e) { log(`write failed: ${e.message}`); }
}
plaintext: SIM (stdin) local: tty virtual na tua máquina
STEP 08 Freebuff processa, escreve resposta daemon/src/index.ts:226-238 (attachTerm) + 81-96 (LineBuffer)

O freebuff corre no PTY. Quando imprime uma linha completa, o daemon particiona por \n e remove ANSI. Cada linha vira um output_chunk distinto.

// daemon/src/index.ts · attachTerm()
t.onData((chunk) => {
  const lines = lineBuf.push(chunk);    // stripAnsi + split '\n'
  for (const line of lines) {
    seq += 1;
    outBuf.push(seq, line);
    sendContent({ type: 'output_chunk', ..., content: line, seq, ... });
  }
});
plaintext: SIM ANSI stripped em stripAnsi()
STEP 09 Daemon cifra (se E2E_on) e responde daemon/src/crypto.ts:99-117 (encryptInner)

Espelha do passo 6 mas com senderRole='daemon'. O AAD passa a "v2|daemon|<seq>" — diferente do AAD do cliente, e essa assimetria é propositada.

// daemon/src/crypto.ts
state.outSeq += 1;
const aad = aadFor('daemon', state.outSeq);   // "v2|daemon|<seq>"
const cipher = crypto.createCipheriv('aes-256-gcm', state.sharedKey, nonce);
cipher.setAAD(aad);
return { v: 2, type: 'enc', seq: state.outSeq,
  nonce: nonce.toString('base64'),
  ct: Buffer.concat([enc, tag]).toString('base64') };
AES-256-GCM AAD: "v2|daemon|<seq>"
STEP 10 Telemóvel recebe e mostra mobile/app.js:174-196 (decryptAndRender)

Decifra, valida AAD, actualiza inSeq. Se for t:'output_chunk', desenha uma bolha verde no chat.

// mobile/app.js
const aad = new TextEncoder().encode('v2|daemon|' + msg.seq);
const plain = await crypto.subtle.decrypt(
  { name: 'AES-GCM', iv: nonce, additionalData: aad },

04

Porque isto é mesmo E2E

três propriedades que importam

1 · A chave privada nunca sai do teu dispositivo

O telemóvel gera um ECDH P-256 keypair efémero em cada pairing. Só a chave pública (clientPub) vai em plaintext para o relay. A chave privada fica na memória do browser. O daemon gera o seu próprio par no arranque. As duas chaves privadas vivem uma no Chrome do telemóvel, outra no Node do daemon.

2 · O segredo partilhado é derivado separadamente em cada lado

Ambos fazem ECDH + HKDF-SHA-256 sobre o mesmo segredo partilhado (matemática do ECDH: privA·pubB = privB·pubA). Resultado: a mesma chave AES-256 em ambos. O relay nunca toca na derivação.

3 · O AAD liga cada ciphertext à sua direcção e posição

O Additional Authenticated Data é "v2|<role>|<seq>". Significa: o relay não pode misturar envelopes entre sessões, nem reordená-los, nem trocar um enc do telemóvel por um do daemon — o auth-tag falha em qualquer troca.
